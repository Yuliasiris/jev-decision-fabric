# Ordinary work SDK preview

Import `createWork`, `restoreWork` and `WorkRun` from `index.mts` (compiled package users use the SDK export). The caller supplies ordinary request text; its native PlannerPort supplies C0 tasks/candidates using registered capability descriptions and actual source views. The user does not author a graph. This adapter contains no native planner, LLM account, Jev connection, database or background worker.

`createWork({requestText, frame, catalog, admission, planner, host, maxPlannerCalls})` returns a run. `await run.run()` invokes the supplied planner, worker/tool, decision and raw-final ports. `run.snapshot()` is a portable wrapper around the original C0 checkpoint. `await restoreWork(snapshot, {catalog, admission, planner, host, restoreChecks})` requires actual latest-store/current-writer/readback authority. It preserves the original run, source frame, deadline, budget, accepted observations and caller reservations.

`host` must bind current authorization/input/freshness checks, original cancellation signal, durable `save` plus exact `readback`, restore acceptance, caller-input/recipient/allocation authorization, planner origin verification, worker archival/origin verification, decision execution and final archival/origin verification. These callbacks are trusted host code and records; no model JSON field supplies authority. A numerical or document host can use ordinary deterministic tools; a live native planner and live Jev decision require the caller's own normal authorized connection. A described capability or finite count is not a permission or spending grant.

Planner initial/next calls use an explicit `maxPlannerCalls` (1..64), retained across restoration. Planner reservations and C0 task/decision reservations share the original `max_operations` total; caller counts and actual nullable usage are reported separately to avoid inventing or duplicating physical charges. The initial ordinary proposal installs tasks with the existing `revise` API, consuming plan version 2 after an empty version-1 admission; therefore `max_plan_versions` must be at least 2. Actual provider allocation/price coverage remains the host's independent responsibility.

Caller reservations, all dispatch frames and the decision admission are durably saved/read back before the corresponding effect. Worker originals are archived, origin/current authorization is rechecked, and accepted completions are saved before dependent work. A save/readback failure stops further effects. Unknown outcomes retain their original reservations and never automatically resend.

`await run.reconcile({observation})`, `{settlement}` or `{planner}` consumes only actual host-verified original records. Unknown settlements stay blocked. `await run.reconcile({final: originalFinalReply})` validates and consumes the previously generated raw answer without invoking another producer. A plain final Observation is rejected. Final JSON has exactly `run_id`, `task_id`, `attempt_id`, `input_digest`, `answer`, `provenance: [{observation_id, claim}]`, and `unresolved`. Its frame and provenance must match the pending reporter and actual accepted reads; quoted text must be present in the host's actual evidence text. These checks do not evaluate paraphrase truth.

`await run.cancel(reason)` durably records cancellation and retains pending physical effects. `await run.continue()` is explicit reentry for a paused caller plan within its same original limits; call `run()` afterward. Failed/cancelled/expired work is not reopened. Actual late or cancelled readback may retain usage under independent record-read authorization, but cannot finish expired work. SDK status separates `COMPLETE`, `PAUSED`, `STOPPED` and `NEEDS_RECONCILIATION`; late known receipts do not become unknown effects, while a pending unreturned decision remains uncertain.

`COMPLETE` describes this SDK's supplied host callbacks, raw-final binding and durable return. It is advisory C0 completion, not Owner acceptance, calibrated truth, live Jev qualification or whole-Goal completion. Inspect actual evidence modes and original receipts. The focused tests use local temporary files, scripted caller/tool/final ports and injected decisions; they perform no network, real provider, deployment or canonical DB operation.
